# Notification outbox is independent of Review Runs

Notification delivery is a side effect of a Review Run, not part of its correctness result. A failed Feishu or WeCom request must not turn a successful human/AI Review Run into a failed Run or prevent another configured channel from being attempted.

The Worker persists one outbox record for each configured channel before delivery. Each channel has a stable explicit ID; outbox routing and its unique key use that ID rather than the channel's list position. Records have their own attempts, lease, claim token, backoff, terminal status and last error. Failed records retry three times by default and remain auditable after the final failure. A correlation ID deduplicates outbox rows for repeated processing of the same Review Run, but cannot prevent a second provider message after a crash between provider acceptance and the outbox update. Feishu/WeCom delivery also requires the provider business response code to indicate success.

The delivery contract is at-least-once: a crash in that window may produce a duplicate provider message. Exactly-once delivery is not assumed because Feishu and WeCom webhooks do not provide a shared transaction with SQLite. The persisted `delivered` state means HTTP and provider business responses accepted the request. It does not prove that a recipient saw the message; canary evidence must record recipient visibility separately.
